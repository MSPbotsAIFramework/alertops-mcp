## Product design

### Goals / Non-goals

**Goals (v1, matches the ticket's wording exactly — review/visibility only):**
- An agent can list and inspect AlertOps alerts for the tenant's account (open/closed/assigned, filterable by status, priority, group, date range).
- An agent can see who is on call right now, optionally scoped to one response group, and can look up a group's on-call schedule/rotation over a date range.
- An agent can list the tenant's AlertOps response groups and see each group's membership (who is in it, their role).

**Non-goals (v1):** creating, updating, closing, assigning, snoozing, or replying to alerts; creating or editing groups, schedules, escalation policies, workflows, services, bridges, topics, or maintenance windows; anything that writes to the tenant's AlertOps account. The ticket only asks for "review" and "visibility" — it does not name any action the agent needs to take in AlertOps. Adding write tools is a separate ticket once a concrete action is requested (see `Decisions made by DEV01` in the Tech design for why this line was drawn here).

### Acceptance criteria AC1..AC9

- **AC1**: Given a tenant's AlertOps API key and open alerts in that account, When an agent calls the "list alerts" tool with no filters, Then it returns a paginated set of alerts (id, status, priority, owner, created date), capped at a default page size, with a flag indicating whether more results exist.
- **AC2**: Given the same key and a `status`/`priority`/`group`/date-range filter, When the "list alerts" tool is called with those filters, Then only alerts matching all given filters are returned.
- **AC3**: Given an existing alert ID, When an agent calls the "get alert" tool, Then the full alert detail is returned (status, owner, escalation policy, SLA state, timestamps). Given an alert ID that does not exist in the tenant's account, Then a structured "not found" error is returned, not a raw exception or a 500.
- **AC4**: Given response groups exist in the tenant's account, When an agent calls the "list groups" tool (optionally with a search term), Then it returns each group's id and name, paginated, filtered to the search term when one is given.
- **AC5**: Given a group ID, When an agent calls the "get group members" tool, Then it returns each member's name, type, and role(s) in that group. Given a group with no members, Then an empty member list is returned, not an error.
- **AC6**: Given no group filter, When an agent calls the "on-call now" tool, Then it returns the current on-call member(s) for every group. Given a specific group ID, Then only that group's current on-call member(s) are returned.
- **AC7**: Given a group ID and a start/end date within AlertOps' own 3-month maximum window, When an agent calls the "get group schedule" tool, Then the schedule/rotation entries covering that window are returned.
- **AC8 (credentials & errors)**: Given a request with no AlertOps credential header, When any tool is called, Then the server returns 401 with a body listing the required header, and makes no outbound call to AlertOps. Given AlertOps itself returns 401/404/429/5xx, Then the tool returns the service's structured error envelope (not a raw exception or an unhandled stack trace).
- **AC9 (tenant isolation)**: Given two concurrent requests carry two different tenants' AlertOps API key headers, When both call the same tool at the same time, Then each response reflects only its own header's AlertOps account — no response, cache, or log line mixes data or credentials from the other request. This is the multi-tenant/isolation anchor for a service with no database of its own: the "tenant boundary" here is the per-request credential header, enforced by the request-scoped context described in the Tech design.

### Open questions

- [not blocking] Whether AlertOps enforces the documented "createdFrom/createdTo must not exceed 6 months" and "schedule date range must not exceed 3 months" limits with a clean 400, or silently truncates, is unconfirmed — AlertOps' own swagger only documents the limit in prose, not in an error schema. **Assumed**: the tool pre-validates the window client-side and returns `invalid_argument` before calling upstream, so behavior is deterministic even if AlertOps' own enforcement turns out to be silent. If a real account later shows AlertOps rejects out-of-range windows differently, the error mapping in `Tech design § Data & API contract` should be adjusted; this does not change any tool's shape or the acceptance criteria above.

## Tech design

### Conclusion

Build the first version of `alertops-mcp` from scratch against AlertOps' public v2 REST API (header-based `api-key` auth), exposing six read-only MCP tools that map directly to the three capabilities the ticket names (alerts, on-call/schedules, group visibility). Python 3.12 + FastMCP + httpx, per the vendor-mcp-development SOP's recommended stack — there is no existing code in this repo to build on or deviate from.

### Where the current implementation lives

Nowhere yet. The repository contains only `README.md` @ 9453815 (one line, no tools). This section is intentionally empty beyond that fact — there is no prior implementation to map.

### Option analysis

| Option | What | Pros | Cost | Verdict |
|---|---|---|---|---|
| AlertOps API v2 (`/api/v2/...`, header `api-key`) | Build all six tools against the v2 REST surface | Credential travels in a header (not a URL query string, so it never lands in access logs); consistent JSON responses; explicit `limit`/`offset` pagination with a documented 100-item hard cap on every list endpoint; richer resource model (alert detail includes escalation policy + SLA state; group detail includes typed member roles) | None material — v2 covers every capability named in the ticket | **Chosen** |
| AlertOps API v1 (legacy, `/api/alert`, `/api/group`, `/api/schedule/...`, `APIKey` as a query parameter) | Build against the legacy RPC-style API instead | Simpler per-endpoint schema | API key travels in the URL query string on every call — it ends up in server access logs and any HTTP proxy/cache between us and AlertOps, which conflicts with the SOP's "credentials only from Header, never logged" rule at the point we call the vendor; schedule responses are less structured (`GetUserSchedule`'s 200 response schema is literally typed `file`) | Rejected — the credential-in-URL shape is the deciding factor, not a stylistic preference |
| Expose AlertOps' full v2 surface (groups/escalation policies/workflows/services/bridges/topics/maintenance windows/alert mutation, ~110 operations) as 1:1 tools | Mirror every v2 endpoint as a tool | Nothing left to add later | Massively over the SOP's ≤20-tool guidance; every mutation endpoint, OTOH, creates write/security surface the ticket never asked for; "group visibility" does not require exposing escalation-policy or workflow CRUD | Rejected — see `Decisions made by DEV01` below for the scoping rule used |

- `src/alertops_mcp/__init__.py` [new] — package marker.
- `src/alertops_mcp/server.py` [new] — `FastMCP(..., stateless_http=True)` app; mounts `POST /mcp` (Streamable HTTP) and `GET /health` (local-only, no upstream call); lifespan mounted on the outer app per SOP §7; `TransportSecuritySettings(enable_dns_rebinding_protection=False)`; listens `0.0.0.0:8080`, overridable via `MCP_HTTP_HOST`/`MCP_HTTP_PORT`; `pydantic-settings` `SettingsConfigDict(extra="ignore")` for forward-compatible env vars.
- `src/alertops_mcp/middleware.py` [new] — reads `X-AlertOps-Api-Key` from the inbound request, stores it in a `contextvars.ContextVar` for the duration of the request (`set` on entry, `reset` in `finally`), returns 401 with the list of required headers when it is missing. - `src/alertops_mcp/tools.py` [new] — the six tool functions (below), each: validates its own arguments, calls `client.py`, maps errors through `errors.py`, returns a compact JSON string (`ensure_ascii=False`, no `indent=2`).
- `tests/test_tools.py` [new] — `tools/list` snapshot; one test per AC1–AC7 behavior against a mocked AlertOps backend (`respx` or `httpx.MockTransport`).
- `tests/test_middleware.py` [new] — missing-header → 401 without an upstream call; concurrent requests with different header values never cross-contaminate (AC9).
- `Dockerfile`, `.dockerignore` [new] — multi-stage build, non-root in the production stage, `curl` installed (slim base lacks it), `EXPOSE 8080`, `HEALTHCHECK` against `/health`, buildable with `--platform linux/amd64`.
- `.gitignore` [new] — `.venv/`, `.env`, `__pycache__/`.
- `README.md` [modify] — product description, the MSPbots Connector boilerplate section (`reference/readme-connector-section.md`, pasted verbatim), the `Authentication headers` table (`X-AlertOps-Api-Key`, required, "AlertOps User API key — AlertOps profile → API Key"), the tool table, and a link to AlertOps' integration overview doc.

#### Tools (the six, with their AlertOps v2 mapping)

| Tool | AlertOps v2 call | Key params | readOnlyHint |
|---|---|---|---|
| `alertops_list_alerts` | `GET /alerts` | `status`, `priority`, `group`, `created_from`, `created_to`, `limit` (default 20, hard cap 100 — AlertOps' own ceiling), `offset` | true |
| `alertops_get_alert` | `GET /alerts/{id}` | `alert_id` | true |
| `alertops_list_groups` | `GET /groups` | `search`, `limit` (default 20, hard cap 100), `offset` | true |
| `alertops_get_group_members` | `GET /groups/{id}/members` | `group_id` | true |
| `alertops_get_oncall_now` | `GET /schedules/oncallnow` | `group_id` (optional) | true |

- **Reuse**: FastMCP for the Streamable HTTP server and stateless-session handling (SOP-recommended, avoids hand-rolling JSON-RPC framing); httpx for the outbound client (async, built-in timeout/retry hooks); pydantic / pydantic-settings for request/response validation and env config. No existing code in this repo to reuse — it is a placeholder README only.
- **New dependencies**: `fastmcp` (MCP server framework, required by the SOP's recommended stack — replaces hand-rolling the MCP protocol), `httpx` (async HTTP client — replaces hand-rolling connection pooling/retries), `pydantic` + `pydantic-settings` (request/response/env validation — replaces manual dict validation). All four are the SOP's standard recommendation for a new Python MCP service, not an independent choice for this ticket.
- **API / parameter shape**: six new tool functions, each taking a flat set of named, optional keyword arguments mirroring the subset of AlertOps' own query parameters it uses (not a single opaque options blob and not one positional parameter per AlertOps filter) — this keeps the signature stable if more of AlertOps' native filters are added later as new optional kwargs, without breaking existing callers.
- **In-scope cleanup**: none — new repository, nothing pre-existing to clean up.
- **Follow-ups (out of this ticket's scope)**: write tools (create/close/assign alerts; create/edit groups, schedules, escalation policies) if a future ticket names a concrete action; escalation-policy and workflow read tools if a future ticket needs them (ticket only asked for alerts/schedules/groups). No table/column deprecation applies — this service has no database.

### Data & API contract

**Credential header** (from the Agent Gateway to this service):

| Header | Required | Meaning |
|---|---|---|
| `X-AlertOps-Api-Key` | yes | The tenant's AlertOps User API key (AlertOps profile → API Key). Sent to AlertOps as the `api-key` header on every upstream call. Never logged, never persisted, never cached across requests. |

**Tool → upstream mapping, with example shapes:**

1. `alertops_list_alerts(status=None, priority=None, group=None, created_from=None, created_to=None, limit=20, offset=0)` → `GET /api/v2/alerts?status=Open&priority=Critical&limit=20&offset=0` with header `api-key: <key>`.
   Response (tool output, compact JSON): `{"alerts":[{"alert_id":51296,"status":"Assigned","priority":"Critical","owner":{"user_name":"jdoe"},"created_date":"2020-09-01T16:59:43"}],"limit":20,"offset":0,"has_more":false}`.
2. `alertops_get_alert(alert_id)` → `GET /api/v2/alerts/{id}`. Not found → `{"error":{"code":"not_found","message":"Alert {id} not found","retryable":false}}`.
3. `alertops_list_groups(search=None, limit=20, offset=0)` → `GET /api/v2/groups?search=...&limit=20&offset=0`. Response: `{"groups":[{"group_id":1000,"group_name":"Support"}],"limit":20,"offset":0,"has_more":false}`.
4. `alertops_get_group_members(group_id)` → `GET /api/v2/groups/{id}/members`. Response: `{"members":[{"member_id":1001,"member_type":"User","member":"testuser1","roles":["Primary","Manager"]}]}`. Empty group → `{"members":[]}`, not an error.
5. `alertops_get_oncall_now(group_id=None)` → `GET /api/v2/schedules/oncallnow` (with `group_id` query param when given). Response: `{"groups":[{"group_id":4649,"group_name":"Test Group","members":[{"name":"Joe Doe","cover_username":"jdoe"}]}]}`.
6. `alertops_get_group_schedule(group_id, start_date, end_date)` → `GET /api/v2/schedules/{group_id}` (date range validated client-side ≤ 3 months before the call; out-of-range → `{"error":{"code":"invalid_argument","message":"Date range must not exceed 3 months","retryable":false}}` without calling AlertOps). In-range response: `{"schedules":[{"schedule_id":"1111","schedule_name":"Test Rotating","schedule_type":"Rotating","start_date":{...},"end_date":{...}}]}`.

**Error envelope** (all tools, on any failure): `{"error":{"code":"<unauthorized|not_found|invalid_argument|rate_limited|upstream_error|not_configured>","message":"<human-readable>","retryable":<bool>}}`. `rate_limited` and `upstream_error` are `retryable: true`; the rest are `false`.

**No database, no migration, no backward-compatibility surface** — this is a new service with no prior consumers.

### Key flow / sequence

```
Agent → Gateway (adds X-AlertOps-Api-Key from the tenant's stored credential)
      → alertops-mcp POST /mcp (tools/call, e.g. alertops_list_alerts)
           → middleware.py: read header into ContextVar, 401 if missing
           → tools.py: validate args → client.py: GET https://api.alertops.com/api/v2/alerts (header: api-key)
           → errors.py maps any non-2xx to the structured envelope
      ← tool returns compact JSON (or the error envelope) ← Gateway ← Agent
```

### Non-functional

- **Idempotency & concurrency**: all six tools are read-only GETs; no write ordering or dedup to reason about. Each request builds its own `httpx.AsyncClient` call from its own `ContextVar` value — no shared mutable state between concurrent requests.
- **Performance**: connect timeout 5s / read timeout 30s per call; retry budget keeps any single tool call under 120s including backoff; list tools default to `limit=20` (well under AlertOps' own 100-item ceiling) to keep MCP response payloads small; responses serialized compactly (`ensure_ascii=False`, no `indent=2`), only the fields named in the contract above are returned (e.g. `alertops_list_alerts` does not pass through AlertOps' full alert object, only the summary fields a list view needs).
- **Security**: `X-AlertOps-Api-Key` is read once per request into a `ContextVar` and never written to logs, disk, or any cache; `.env`/`.venv` are git- and docker-ignored; `gitleaks detect` runs before first delivery (SOP §11); no hardcoded credentials anywhere in the repo (README uses a placeholder like `ak_xxx`).
- **Multi-tenant isolation**: this service has no database — the tenant boundary is the per-request `X-AlertOps-Api-Key` header. The `ContextVar` is `set` at the start of the request and `reset` in a `finally` block so one request can never read another's in-flight value; no global/module-level variable ever holds a credential or a response; the httpx client is constructed per call, not pooled with a baked-in credential. This is AC9's enforcement mechanism.
- **Observability**: structured log line per tool call with request id, tool name, upstream HTTP status, and latency — never the header value or the full response body; a counter of upstream status codes (2xx/4xx/5xx) to spot AlertOps-side degradation.

### Decisions made by DEV01

No one was available to ask (unattended design tick); these are the first-version judgment calls, each reversible by a follow-up ticket:

- **Chose AlertOps API v2 over the legacy v1 API** — v2 carries the API key in a request header (`api-key`), matching the SOP's "credentials only from Header, never in a URL" rule all the way to the vendor call; v1 passes `APIKey` as a query-string parameter on every endpoint, which would land the tenant's key in access logs between us and AlertOps. Alternative considered: v1 (rejected for the query-string credential exposure, not a stylistic preference).
- **First version is read-only** (list/get alerts, list groups, group members, on-call now, group schedule) — the ticket's own wording is "review ... and group visibility", naming no action. Alternative considered: mirror AlertOps' full v2 surface (~110 operations including alert creation/close/assign, group/schedule/escalation-policy/workflow/service/bridge CRUD) — rejected as far outside the SOP's ≤20-tool guidance and as scope the ticket never asked for; write tools are a follow-up ticket if a concrete action is requested.
- **Credential model**: a single vendor API key via `X-AlertOps-Api-Key`, registered as a plain (non-OAuth) vendor. AlertOps only supports a per-user API key, so there was no alternative to weigh.
- **List pagination defaults**: `limit=20` default / `100` hard cap (AlertOps' own ceiling) for `alertops_list_alerts` and `alertops_list_groups`. Alternative considered: SOP's looser default of up to 50 — chose a smaller default given alert objects can carry a free-text description field, to keep typical responses well under the SOP's 20000-character budget.
- **Group detail exposed via `alertops_get_group_members` rather than mirroring `GET /groups/{id}`** — the ticket asks for "group visibility" (who is in a group), and `/groups/{id}/members` returns exactly that without the escalation-policy and dynamic-group metadata `/groups/{id}` also carries, which nothing in the ticket asked for. Alternative considered: expose `/groups/{id}` verbatim — rejected as carrying fields with no named use yet (can be added later if asked).
